# Zoro Learning System - Node-Based Planning Workflow

## BEFORE STARTING ANY TASK

**NODE-BASED WORKFLOW:** Before implementing any task, you MUST:

1. **Generate execution plan with persistent chat-id**:
   ```bash
   zoro plan "<task description>" --chat-id <unique-id>
   ```
   - Creates `.rules/zoro_plan.md` (markdown - always current!)
   - Creates `.zoro/generated/assistant/<chat-id>/plan.json` (JSON source of truth)
   - Markdown auto-syncs on every update!

2. **Read the generated plan**:
   ```bash
   read_file .rules/zoro_plan.md
   ```
   DO NOT GENERATE A PLAN IN A DIFFERENT FILE. REPLACE THE EXISTING FILE IF THERE IS A NEW PLAN.

3. **Follow the plan and track progress**:
   - Execute steps in order based on their node type
   - Apply rules listed for each step
   - Monitor for failure points mentioned in each step
   - **Update status as you work** (see Tracking Commands below)
   - If a step is type "planning", run `zoro plan-iter` after completing it

4. **If you detect a failure point**:
   - Stop current approach
   - Refer to the guardrail in the plan
   - Adjust and continue with the lesson learned

## Node Types

Plans are structured using 5 node types that define how to approach each step:

### 1. checking-with-user ✅
**Purpose:** Iteratively clarify requirements until fully understood
**Behavior:** 
- Ask 2-3 clarifying questions per round
- Review existing rules from past tasks for patterns/conflicts
- Continue asking until confident (low/medium/high confidence tracking)
- Present final requirements checklist + **user story** for user approval
**Output:** Approved requirements checklist + user story (saved to node.output)

**User Story Format:**
```json
{
  "requirements_checklist": [
    "✓ Requirement 1",
    "✓ Requirement 2"
  ],
  "user_story": {
    "title": "Brief feature name",
    "flow": [
      "1. User does X",
      "2. System responds with Y",
      "3. User sees Z",
      "4. End state: ..."
    ],
    "expected_outcome": "What the user achieves end-to-end"
  }
}
```

**CRITICAL:** User story must describe the COMPLETE end-to-end user journey:
- Start from user's perspective (not implementation details)
- Show sequential steps: user action → system response → next action
- Include what user sees/experiences at each step
- End with final outcome/state
- User MUST verify this flow before proceeding

**Example Questions:**
- "Email or username login?"
- "Password requirements? (length, complexity)"
- "Where should validation errors display?"

**When Complete:** 
1. Save requirements + user story: `zoro set-output step-1 "<json>"`
2. Move to planning node

### 2. planning 🌍
**Purpose:** Global codebase analysis and implementation strategy design
**Behavior:**
- Analyze good/bad trajectories from similar past tasks
- Read relevant files to understand current architecture
- Identify dependencies and relationships
- Design high-level implementation approach
- Break down approach into 3-5 code-style steps
- **Present strategy to user for approval**
- **IMPORTANT:** When completing this node, write your full strategy to `node.output` field (see below)
- After approval, **auto-generates code-style nodes** via `plan-iter`

**Output:** Implementation strategy + auto-generated code-style steps

**How to Save Strategy (REQUIRED):**
When you complete the planning node, use `attempt_completion` with a command that saves your strategy:
```bash
# Save your strategy to the planning node's output field
# This will be used by plan-iter to generate code-style steps
echo "Your full implementation strategy here..." | zoro set-output step-2
```
Or let Cline know to save the strategy in the node's output via the API.
**Example Strategy:**
```
Files analyzed: LoginForm.tsx, auth.py, schemas.py
Approach:
1. Update schema (add validation fields)
2. Create /api/validate endpoint
3. Add frontend form with error display
```

**Action After User Approves:**
```bash
zoro plan-iter "implement strategy" --from-step 3
```
This automatically generates code-style nodes (steps 3-5) in the plan.

### 3. code-style 🔨
**Purpose:** Tactical implementation following planning blueprint
**Generated By:** planning node (via plan-iter)
**Key Feature:** Contains **substeps** for incremental implementation
**Cannot Exist:** Before a planning node completes
**Example substeps:**
1. Add new field to User model
2. Create migration file  
3. Update API endpoint
4. Add frontend validation

Each substep implements 1-2 features at a time - DO NOT implement everything at once.

### 4. debugging 🐛
**Purpose:** Fix unexpected errors
**Triggered By:** User manually adds node describing the problem
**Behavior:** Cline analyzes error and proposes fix
**Example:** User adds: "Getting 404 on /api/tasks endpoint"

### 5. testing ✅
**Purpose:** Verify correctness and robustness
**Status:** Not yet implemented (future enhancement)

## Tracking Commands (Keep Plan Updated)

**All tracking commands auto-update `.rules/zoro_plan.md`** - just re-read it to see changes!

### Update Step Status
```bash
zoro update-step <step-id> <status>
```

**Statuses:**
- `pending` - Not started yet
- `in_progress` - Currently working on this
- `completed` - Done (or use `complete-step` below)
- `blocked` - Stuck, can't proceed

**Example:**
```bash
zoro update-step step-1 in_progress
# Re-read plan: "Status:" line updates
```

### Add Notes to Step
```bash
zoro add-note <step-id> "note text"
```

**Example:**
```bash
zoro add-note step-1 "Decided to use Yup for validation"
# Re-read plan: note appears in step's Notes section
```

### Complete Step (with rule tracking)
```bash
zoro complete-step <step-id> [--rules-used "rule-id-1,rule-id-2"]
```

**Example:**
```bash
zoro complete-step step-1 --rules-used "abc-123,def-456"
# Re-read plan: status becomes "completed", audit trail shows rules used
```

### Update Substep
```bash
zoro update-substep <step-id> <substep-id> <status>
```

**Rule:** For **code-style** steps, treat substeps as the real unit of progress. After you finish a substep, mark it:
```bash
zoro update-substep step-2 substep-1 completed
```
This is what drives the **frontend checkbox state** (`substep.completed`).

**Example:**
```bash
zoro update-substep step-3 substep-1 completed
# Re-read plan: substep line shows "\\[x\\]" for completed
```

## Generating Code-Style Steps with plan-iter

After completing the "planning" node, you generate implementation steps:

1. **Complete the planning step** (analyze codebase, design strategy, get user approval)
2. **Generate code-style steps:**
   ```bash
   zoro plan-iter "implement login validation strategy" --chat-id <same-id> --from-step 3
   ```
   - Uses `GENERATE_CODE_STYLE_STEPS_PROMPT` 
   - Analyzes good/bad trajectories
   - Creates 3-5 code-style nodes with substeps
   - Adds rules to each new step
3. **Read updated plan** - it will contain the new code-style steps
   ```bash
   read_file .rules/zoro_plan.md
   ```
4. **Execute code-style steps** sequentially

The `plan-iter` command generates NEW nodes and adds them to the plan.

## Editing Existing Steps with plan-edit

If you need to modify existing steps after they've been created:

1. **Run plan-edit:**
   ```bash
   zoro plan-edit "optimize for performance" --chat-id <same-id> --from-step 4
   ```
   - Uses `REWRITE_STEP_PROMPT` and `REWRITE_SUBSTEPS_PROMPT`
   - Rewrites step-4 onwards in place
   - Preserves completion status of substeps
2. **Read updated plan**
   ```bash
   read_file .rules/zoro_plan.md
   ```

The `plan-edit` command modifies existing nodes without adding new ones.

## Failure Detection

Watch for these indicators that you may have hit a failure point:
- User asks you to redo something you just did
- User corrects assumptions you made
- User says "no" or "that's not what I meant"
- You're building something without full requirements
- You're installing packages without confirmation

When detected:
1. **If guardrail is clear** - Apply it directly and adjust approach
2. **If significantly off-track** - Stop and re-run planning for the same chat-id:
   ```bash
   zoro plan "<what went wrong>" --chat-id <same-id>
   ```
   (Optional) If you need to rewrite future steps in the current plan:
   ```bash
   zoro plan-iter "<refinement>" --chat-id <same-id> --from-step <N>
   ```

## CLI Command Quick Reference

### Planning
- `zoro plan "<task>" --chat-id <id>` - Generate new 2-node plan (checking-with-user + planning)
- `zoro plan-iter "<strategy>" --chat-id <id> --from-step <N>` - Generate new code-style steps
- `zoro plan-edit "<changes>" --chat-id <id> --from-step <N>` - Edit existing steps

### Tracking
- `zoro update-step <step-id> <status>` - Update status (pending|in_progress|completed|blocked)
- `zoro add-note <step-id> "text"` - Add note to step
- `zoro complete-step <step-id> [--rules-used "ids"]` - Mark complete + log rules
- `zoro update-substep <step-id> <substep-id> <status>` - Update substep (pending|completed)
- `zoro set-output <step-id> "output text"` - Save execution output (e.g., planning strategy)

### Utilities
- `zoro search "<query>"` - Search learned rules
- `zoro messages <file>` - Extract user messages from chat

**Remember:** `.rules/zoro_plan.md` auto-updates on every tracking command!
